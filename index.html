NVIDIA DGX
At-Home AI Stack

Complete self-hosted AI server stack on the Nvidia DGX Spark (arm64). Covers model serving, proxying, workflow automation, agent layer, and multi-client access. Follow each step in order to replicate on a fresh machine.

Qwen3.6-35B-A3B-FP8 vLLM 0.19 LiteLLM Hermes Agent n8n Open WebUI Telegram gateway arm64 native

Architecture

Prerequisites

  • Nvidia DGX Spark — Grace CPU, GB10 GPU, arm64/aarch64
  • Ubuntu 24.04
  • Docker installed and enabled: sudo systemctl enable docker
  • Replace YOUR_USERNAME with your Linux username throughout
  • Replace YOUR_SERVER_IP with your server's LAN IP throughout
STEP 01

vLLM + Qwen3.6-35B

vLLM runs as a standalone Docker container on port 8000 with tool calling, chunked prefill, prefix caching, and reasoning parser enabled.

bash
docker run -d \
  --name vllm-qwen-35b \
  --gpus all \
  -p 8000:8000 \
  -v ~/.cache/huggingface:/root/.cache/huggingface \
  --ipc=host \
  --ulimit memlock=-1 \
  --ulimit stack=67108864 \
  nvcr.io/nvidia/vllm:26.04-py3 \
  vllm serve Qwen/Qwen3.6-35B-A3B-FP8 \
    --served-model-name qwen3.6-35b \
    --dtype auto \
    --gpu-memory-utilization 0.8 \
    --max-model-len 131072 \
    --enable-auto-tool-choice \
    --tool-call-parser qwen3_coder \
    --enable-chunked-prefill \
    --enable-prefix-caching \
    --max-num-seqs 32 \
    --port 8000 \
    --reasoning-parser qwen3 \
    --default-chat-template-kwargs '{"preserve_thinking": true}'

Set restart policy so vLLM survives reboots:

bash
docker update --restart unless-stopped vllm-qwen-35b

Wait ~7 minutes for the model to load, then verify:

bash
curl http://localhost:8000/v1/models
Expected: {"data":[{"id":"qwen3.6-35b",...}]}
⚠
On first boot after a reboot, vLLM may fail with CUDA driver error: operation not permitted — a stale Triton compile cache in /tmp. Fix:

docker exec vllm-qwen-35b rm -rf /tmp/torchinductor_root /root/.cache/vllm/torch_compile_cache/torch_aot_compile
docker restart vllm-qwen-35b

STEP 03

LiteLLM config

LiteLLM proxies all client requests to vLLM and logs every request/response to SQLite — the foundation for future fine-tuning.

bash
cat > litellm-config.yaml << 'EOF'
model_list:
  - model_name: qwen3.6-35b
    litellm_params:
      model: openai/qwen3.6-35b
      api_base: http://localhost:8000/v1
      api_key: "not-needed"

litellm_settings:
  verbose: true
  database:
    type: sqlite
    path: /app/logs/litellm.db
  log_config:
    level: INFO
    format: json
    filepath: /app/logs/litellm.log

router_settings:
  num_retries: 0
  timeout: 600
EOF

bash

[Service]
Type=simple
User=YOUR_USERNAME

ExecStart=/home/YOUR_USERNAME/.local/bin/litellm --config litellm-config.yaml --port 8001

OBSIDIAN LIVESYNC

Vault sync + AI query pipeline

A self-hosted Obsidian vault sync and AI query pipeline running entirely server-side, with no laptop dependency. Mac and Android devices sync their Obsidian vaults bidirectionally to CouchDB on a dedicated Proxmox LXC. A Go exporter reassembles the chunked documents into flat Markdown files, and an MCP filesystem server exposes the vault to LiteLLM — so any client (Telegram, Hermes, n8n, Open WebUI) can query your notes as a tool call.

Why a separate LXC?

The DGX Spark's 128 GB of RAM is fully committed at idle with vLLM, LiteLLM, Open WebUI, and n8n running (~114 GB in use). Adding CouchDB directly on the Spark would compete with model weights. Running vault services on a lightweight Proxmox LXC keeps inference RAM entirely dedicated to vLLM.

Architecture flow

Mac/Android (Obsidian + LiveSync)
        ↓ bidirectional sync
CouchDB 3.5.1 (Proxmox LXC · obsidian-livesync)
        ↓ poll every 30s
livesync-exporter → /vault/*.md
        ↓
MCP filesystem server (@mcp/server-filesystem)
        ↓ via Tailscale VPN
LiteLLM (DGX Spark · port 8001)
        ↓
Telegram · Hermes · n8n · Open WebUI

Components

ComponentWhat it doesWhere
CouchDB 3.5.1Receives LiveSync sync from all clients; stores vault in chunked formatProxmox LXC
livesync-exporterGo binary; polls CouchDB every 30 s, reassembles children chunk arrays via _bulk_get, writes flat .md files to /vault/Proxmox LXC
MCP filesystem server@modelcontextprotocol/server-filesystem pointed at /vault/; exposes vault to LiteLLM as a toolProxmox LXC
TailscalePrivate network between LXC and DGX Spark for MCP connectionBoth nodes

OBSIDIAN LIVESYNC

Roadblocks & solutions

DGX Spark memory pressure
ProblemSpark had 114 GB of 128 GB RAM in use at idle (vLLM, LiteLLM, Open WebUI, n8n). No headroom for additional resident services.
FixDeployed CouchDB and all vault-related services on a dedicated Proxmox LXC, keeping the Spark exclusively for inference workloads.
Ubuntu Oracular (24.10) EOL on existing LXC
ProblemInitial LXC provisioned with Ubuntu 24.10 (Oracular) hit EOL. All apt repos returned 404, making the container unusable.
FixProvisioned a fresh LXC with Ubuntu 24.04 LTS (Noble). All new LXCs now use 24.04 LTS or Debian 12.
CouchDB Erlang node name mismatch
ProblemStandard node path _node/nonode@nohost in CORS configuration commands returned nodedown errors.
FixQuery /_membership to discover the actual node name (couchdb@127.0.0.1) and substitute it in all configuration commands.
CouchDB account lockout
ProblemCORS curl commands pasted with placeholder password instead of real credentials triggered CouchDB's brute-force lockout after repeated failures.
Fixsystemctl restart couchdb clears the lockout. Re-run all CORS configuration commands with the correct password.
LiveSync chunked storage format
ProblemInitial livesync-exporter assumed documents stored content in a data field. LiveSync uses a chunked architecture — each file document has a children array of chunk IDs (prefixed h:), with content split across multiple leaf documents.
FixRewrote exporter: fetch file docs → collect all chunk IDs from children arrays → bulk-fetch via _bulk_get → reassemble content in order → write to /vault/.
LITELLM + OBSIDIAN MCP

LiteLLM centralized MCP + Obsidian vault

This report documents every bug and fix encountered while integrating LiteLLM's MCP gateway with the Obsidian vault pipeline. The goal: centralize vault access as a single MCP server in LiteLLM so all clients (Telegram via Hermes, Open WebUI, n8n, API) can query vault notes through one gateway with no client-side configuration or laptop dependency.

Mac/Android (Obsidian + LiveSync)
        ↓ sync
CouchDB (Proxmox LXC, 10.10.15.10)
        ↓ poll every 30s
livesync-exporter (Go binary) → /vault/*.md
        ↓
supergateway + mcp-server-filesystem → :3000
        ↓
LiteLLM (Spark, port 8001) — MCP gateway
        ↓
All clients: Telegram · Hermes · Open WebUI · API
⚠18 issues across 4 areas: LXC container setup, LiteLLM MCP integration, Hermes Agent, and Open WebUI. All resolved except the LiteLLM Playground UI rendering bug — the backend works correctly.
LITELLM + OBSIDIAN MCP

LXC container issues (1–7)

Issue 1 — Ubuntu Oracular (24.10) EOL
Symptomapt update failed — all package repos returned 404.
CauseInitial LXC provisioned with Ubuntu 24.10 (Oracular), which reached EOL July 2025.
FixScrapped container, provisioned fresh Ubuntu 24.04 LTS (Noble) LXC. Rule going forward: always use LTS releases for infrastructure containers.
Issue 2 — CouchDB Node Name Mismatch
SymptomCORS config commands returned {"error":"nodedown","reason":"nonode@nohost is down"} even after CouchDB was running.
CauseDefault CouchDB docs reference nonode@nohost but the actual Erlang node name on Ubuntu is couchdb@127.0.0.1.
bash
curl http://localhost:5984/_membership
# → {"all_nodes":["couchdb@127.0.0.1"],"cluster_nodes":["couchdb@127.0.0.1"]}
FixAlways query /_membership first to confirm the real node name. Use couchdb@127.0.0.1 in all config commands.
Issue 3 — CouchDB Account Lockout
SymptomAll API calls returned {"error":"forbidden","reason":"Account is temporarily locked due to multiple authentication failures"}.
CauseSeveral curl commands ran with the literal placeholder yourpassword instead of real credentials, triggering the lockout.
Fixsystemctl restart couchdb clears the lockout counter immediately.
Issue 4 — livesync-exporter: Wrong CouchDB Document Structure
SymptomExporter logged "Exported 74 files" every 30s but /vault/ remained empty.
CauseInitial Go exporter assumed content lived in a data field. LiveSync uses a chunked format — file docs contain only a children array of chunk IDs (h: prefix); content lives in separate chunk documents.
json
// File document — metadata only
{ "_id": "00 - daily/2026-04-04.md", "children": ["h:3v14o1...", "h:32d9gh..."], "type": "plain" }

// Chunk document — actual content
{ "_id": "h:3v14o1...", "data": "...content fragment..." }
FixRewrote exporter: (1) fetch file docs, skipping h:/ps:/ix:/_-prefixed docs, (2) extract children chunk IDs, (3) bulk-fetch via _bulk_get, (4) concatenate in order, (5) write to /vault/.
Issue 5 — Node.js v18 Segfaults
Symptommcp-server-filesystem crashed with SIGABRT (exit code 134) when supergateway tried to spawn it.
CauseNode.js 18.19.1 on the LXC was incompatible with the installed version of mcp-server-filesystem.
bash
curl -fsSL https://deb.nodesource.com/setup_20.x | bash -
apt install -y nodejs
FixUpgrade to Node.js 20 via NodeSource. Crashes resolved entirely.
Issue 6 — supergateway Stateless Mode Process Explosion
Symptommcp-server-filesystem processes accumulated under load, eventually hitting pthread_create: Resource temporarily unavailable and crashing the MCP server.
Causesupergateway in default stateless mode spawns a new mcp-server-filesystem child process per incoming HTTP request. Under concurrent load these accumulate and exhaust thread limits.
bash
ExecStart=supergateway \
  --stdio "npx @modelcontextprotocol/server-filesystem /vault" \
  --port 3000 \
  --outputTransport streamableHttp \
  --stateful \
  --sessionTimeout 300000
FixAdd --stateful --sessionTimeout 300000. Maintains a single persistent child process with session management instead of spawning per request.
Issue 7 — LXC Filesystem Corruption After Forced Restart
SymptomAfter attempting to set lxc.pids.max and rebooting, LXC failed to start with run_buffer: Script exited with status 255.
CauseThe forced reboot left the ext4 journal dirty on the raw disk image.
bash
# Run from the Proxmox host, not inside the LXC
e2fsck -f /mnt/pve/J-PROX-CTS/images/100/vm-100-disk-0.raw
pct start 100
Fixe2fsck replays the journal and recovers the filesystem. Run from the Proxmox host.
LITELLM + OBSIDIAN MCP

LiteLLM MCP integration issues (8–13)

Issue 8 — tool_choice: auto Sent Without tools Array
SymptomEvery LiteLLM playground request with MCP servers selected returned 400: ValueError: When using tool_choice, tools must be set.
CauseLiteLLM MCP integration sends tool_choice: auto on the initial request before the tools list is attached. vLLM correctly enforces the OpenAI spec — tool_choice without tools is invalid. Confirmed LiteLLM bug.
Dead endsdrop_params: true doesn't strip tool_choice. modify_params: true adjusts formatting, not logic. No UI setting exists.
bash
docker exec vllm-qwen-35b sed -i \
  's/            if "tools" not in data or data\["tools"\] is None:/            if ("tools" not in data or data["tools"] is None) and data["tool_choice"] != "auto":/' \
  /usr/local/lib/python3.12/dist-packages/vllm/entrypoints/openai/chat_completion/protocol.py
docker restart vllm-qwen-35b
FixPatched vLLM inside the container to skip validation when tool_choice is auto and no tools are present. ⚠️ Patch lives inside the container — reapply if the container is recreated.
Issue 9 — MCP Servers Disappear from UI After Restart
SymptomAfter every LiteLLM restart, MCP Servers page shows empty. /v1/mcp/server returns []. Records exist in Postgres.
CauseLiteLLM UI/API cache bug — server list not refreshed from DB on startup.
WorkaroundAdd a dummy MCP server in the UI then delete it. Forces a UI refresh and real entries reappear.
yaml
# litellm-config.yaml — top level, NOT nested under litellm_settings
mcp_servers:
  obsidian:
    url: "http://10.10.15.10:3000/mcp"
    description: "Read, search, and manage Obsidian vault notes and files"
FixDefine MCP servers at the top level of litellm-config.yaml. Config-file servers load on startup regardless of DB cache state. Confirmed by grepping proxy_server.py: mcp_servers_config = config.get("mcp_servers", None).
Issue 10 — Missing litellm-dashboard Team Blocking MCP Tool Listing
SymptomEvery MCP tool listing attempt: 404: Team doesn't exist in db. Team=litellm-dashboard.
CauseLiteLLM's MCP permission system references a default team litellm-dashboard that should be auto-created on first run but wasn't.
bash
curl -X POST http://localhost:8001/team/new \
  -H "Authorization: Bearer sk-your-master-key" \
  -H "Content-Type: application/json" \
  -d '{"team_id": "litellm-dashboard", "team_alias": "LiteLLM Dashboard"}'
FixManually create the litellm-dashboard team via the API. Only needs to be done once.
Issue 11 — MCP Timeout Was Actually a Crash, Not a Timeout
SymptomMCP client list_tools was cancelled and Timeout while listing tools from obsidian in LiteLLM logs.
CauseThe MCP server was crashing mid-request (Issues 5 & 6). The "timeout" was the client giving up after the connection dropped — not a real 60s timeout.
Dead endmcp_settings.timeout under litellm_settings does not map to MCP_CLIENT_TIMEOUT. That constant reads from the LITELLM_MCP_CLIENT_TIMEOUT env var, not the config file. The key was silently ignored.
FixResolved by fixing the underlying Node.js/supergateway issues (5 & 6). No timeout tuning was needed.
Issue 12 — system_prompt in litellm_params Not Injected as System Message
SymptomModel ignored instructions to use /vault as base path and responded without vault context.
Causesystem_prompt under litellm_params is sent as a top-level field in the request body — not inserted into the messages array. vLLM passes it through as an unknown field and the model never sees it.
yaml
litellm_settings:
  default_system_message: "You have access to an Obsidian vault via MCP tools.
    All vault files are located at /vault. When searching the vault, always use
    /vault as the base path. Never use '.' as a path. Complete all tool calls
    and searches fully before responding — never stop mid-task."
FixUse default_system_message under litellm_settings — this correctly injects the instruction into the messages array.
Issue 13 — LiteLLM Playground UI Drops Response After Tool List
SymptomPlayground lists all 14 obsidian tools, spinner runs, then the entire response box disappears. No errors in LiteLLM logs — all requests return HTTP 200.
CauseLiteLLM Playground UI rendering bug — the streaming multi-turn MCP response format isn't handled correctly by the frontend.
FixNo fix available. Use the API or other clients — the backend works correctly. Direct curl calls return full tool results and vault content.

Hermes & Open WebUI issues (14–18)

Hermes Agent

Issue 14 — Hermes Gateway Auth Failure After Master Key Added
Symptomhermes-gateway.service crashed: AuthenticationError [HTTP 401]: LiteLLM Virtual Key expected. Received=no-key-required, expected to start with 'sk-'.
CauseHermes config had api_key: "no-key-required" — worked before LiteLLM required authentication via master key.
FixUpdate ~/.hermes/config.yaml with a valid LiteLLM virtual key.
Issue 15 — Hermes Using Built-in Obsidian Skill Instead of MCP
SymptomHermes ignored the MCP server and tried to read vault files from ~/Documents/Obsidian Vault on the Spark (path doesn't exist).
CauseHermes has a built-in obsidian skill that uses local filesystem commands. It activates before MCP tools when vault-related queries are made.
yaml
# ~/.hermes/config.yaml
mcp_servers:
  obsidian:
    url: "http://10.10.15.10:3000/mcp"
    transport: streamableHttp
FixAdd MCP server to Hermes native MCP config. Patch ~/.hermes/skills/note-taking/obsidian/SKILL.md to instruct Hermes to always use MCP tools and /vault as base path when an MCP server is configured.
Issue 16 — localhost vs host.docker.internal Shared Config Conflict
SymptomChanging base_url to host.docker.internal fixed hermes-webui (Docker container) but broke hermes-gateway (systemd host service). host.docker.internal doesn't resolve on the host itself.
CauseBoth services share ~/.hermes/config.yaml. The URL that works inside Docker doesn't work on the host, and vice versa.
FixKeep base_url: http://localhost:8001/v1 in config. Docker's extra_hosts: ["host.docker.internal:host-gateway"] in docker-compose.yml makes host.docker.internal resolve correctly inside the container — while localhost works on the host. Same config file, both contexts resolve correctly.

Open WebUI

Issue 17 — Open WebUI Built-in search_notes Tool Overriding MCP
SymptomVault queries used a search_notes tool that returned empty results instead of the LiteLLM obsidian MCP tools.
CauseOpen WebUI has a built-in search_notes tool for Obsidian. It executes at the Open WebUI layer before the request reaches LiteLLM's MCP gateway, looking for a local vault path that doesn't exist on the Spark.

TROUBLESHOOTING

LiteLLM Admin UI

The LiteLLM proxy ships with a built-in web UI at /ui. It requires a master key and a PostgreSQL database — SQLite is not supported for the UI auth layer. The following documents every error encountered during setup, in order.

Step 1 — Set a master key

Add to ~/sparky-ai-stack/litellm-config.yaml:

yaml
general_settings:
  master_key: sk-yourkey
  database_url: "postgresql://litellm:litellm@localhost:5432/litellm"

Generate a secure key:

bash
echo "sk-$(openssl rand -hex 16)"

Step 2 — Add PostgreSQL to docker-compose.yml

Rather than a standalone docker run command, declare it as a service in ~/sparky-ai-stack/docker-compose.yml so the entire stack is managed as a single unit — one docker compose up starts everything, volumes are declared alongside the services that use them, and restart behavior is consistent.

yaml
  litellm-db:
    image: postgres:16
    container_name: litellm-db
    restart: unless-stopped
    environment:
      - POSTGRES_USER=litellm
      - POSTGRES_PASSWORD=litellm
      - POSTGRES_DB=litellm
    ports:
      - "5432:5432"
    volumes:
      - litellm_db:/var/lib/postgresql/data

volumes:
  litellm_db:
bash
docker compose up -d litellm-db
ℹrestart: unless-stopped combined with sudo systemctl enable docker ensures the container survives reboots automatically — no additional systemd unit needed.

Step 3 — Install Prisma

LiteLLM uses Prisma as its database ORM. It is not included in the base pip install litellm package.

bash
pip install prisma --break-system-packages

--break-system-packages bypasses a Python 3.12 restriction that prevents pip from installing into the system Python environment. It is safe on a dedicated AI server where system tools do not depend on conflicting packages.

Step 4 — Generate Prisma binaries

After installing the package, the binaries must be generated from LiteLLM's bundled schema:

bash
cd ~/.local/lib/python3.12/site-packages/litellm/proxy
prisma generate --schema schema.prisma

Step 5 — Apply the database schema

The Postgres database exists but has no tables yet. Push the schema. DATABASE_URL must be passed inline — Prisma reads it directly from the environment, not from litellm-config.yaml.

bash
DATABASE_URL="postgresql://litellm:litellm@localhost:5432/litellm" \
prisma db push --schema schema.prisma

Step 6 — Restart LiteLLM

bash
sudo systemctl daemon-reload
sudo systemctl restart litellm
sudo systemctl status litellm
